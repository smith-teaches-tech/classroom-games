Editing Your Site

Building with AI — the tools, the loop, and getting your work online

Your homepage is still a mockup someone handed you. Today it becomes yours — and you learn the workflow you'll use for every project after this one.
What you're making today is a homepage you'd actually send someone. Not a starter template with your name swapped in — colours you chose, words you wrote, a layout you decided on. Everything else here is how you get that safely onto the internet.

The loop, start to finish

GitHub Desktopcopy it down ▸ VS Codeopen it ▸ Geminiredesign it ▸ VS Codepaste & save ▸ GitHub Desktopcheck & push ▸ Your sitetest it

Three apps, each doing one job. GitHub Desktop moves your files between your computer and GitHub. VS Code is where the files get edited. Gemini writes the new version. Nothing overlaps, so when something goes wrong you'll know which window to look at.

PART 1Install your tools

Two apps. Both free, both quick.

ObjectiveGitHub Desktop and VS Code installed and signed in, ready to use.

GitHub Desktop

desktop.github.com → download → install → open it.

Sign in with your GitHub account. That one sign-in is what lets it read and write your repository. You won't be asked again.

VS Code

code.visualstudio.com → download → install → open it.

No sign-in needed. Skip any setup questions it asks — you can change all of that later.

Same app on Mac and Windows. Both of these look and work identically on either. When your teacher demonstrates on one, it's the same on the other — only the keyboard shortcuts differ, and this page gives both.

Nothing to install

Neither of those apps runs on an iPad — but you don't need them, because you get the same tools in the browser.

github.dev is a real code editor. It's the same editor as VS Code, running in Safari, and it can do the GitHub Desktop part too.

This is a promotion. Until now you've been pasting code into a box on a web page. Today you get the actual editor — files in a sidebar, several open at once, and a proper view of what you've changed.

You'll open it in the next part. Nothing to do here.

PART 2Get your site into your editor

Copy it down from GitHub, then open the folder.

ObjectiveYour repository open in an editor, with your files listed down the side.

Clone it

Cloning means copying your repository from GitHub down onto your computer.

your repo on github.com▸ Code ▾▸ Open with GitHub Desktop

A Clone a Repository window opens with a Local Path box. Click Choose… and pick somewhere you'll actually find again — your Desktop is fine. Then click Clone.

Write down where it went. The most common problem in this lesson is a student who cloned their repository and then cannot find it. Open the folder right now and look at it before moving on.
You now have two folders and only one counts. Your old project folder from earlier this term is history — a snapshot of how things were. The cloned repository is the real one from today onward. Everything you change happens in there.

Open it in VS Code

In GitHub Desktop, click Open in Visual Studio Code. (Or in VS Code: File → Open Folder… and pick your cloned folder.)

VS Code will ask whether you trust the folder. Click Yes, I trust the authors — it's your own work.

What you're looking at. Down the left is every file in your repository. That sidebar is your repo — the same files you saw on GitHub, now on your machine.

Click index.html — the one at the top of the list, not the one inside your project folder. That's your homepage.

Open github.dev

Go to your repository on github.com, then either:

  • Press the . key (a full stop), or
  • Change github.com to github.dev in the address bar

Your whole repository opens in an editor. Files down the left, code in the middle.

Click index.html — the one at the top of the list, not the one inside your project folder. That's your homepage.

Nothing gets copied to your iPad. You're editing GitHub's copy directly, which means there's no folder to lose — but you do need to stay online. If the . shortcut does nothing on your keyboard, type the address by hand.

PART 3Redesign it with Gemini

This is the actual work today. The rest is plumbing.

ObjectiveA homepage that looks like somebody designed it on purpose — specifically, you.

What you've got right now is a mockup. It works, and it looks like it works, and that's all it does. Here's what separates a page that was designed from one that was merely finished:

Colour

Pick your own — two or three, deliberately. A background, a text colour, one accent. The starter's grey was a placeholder, not a decision.

Type

One font choice changes everything. Anything is more interesting than the browser default, which is what you have now.

Space

Crowded pages read as unfinished. Give headings room above them and let things breathe.

Words

"Things I'm building" is filler. Say something true and specific about what you make. This is the part people actually read.

Copy your file into Gemini

In your editor, click inside index.html, select everything — Mac: ⌘A  Windows: Ctrl+A — and copy.

Open Gemini, paste it in, and use this:

Here is my portfolio homepage. Redesign how it looks.

What I want: [describe the colours, the mood, the font feel,
and how spacious or dense it should be — be specific,
"make it look cool" gets you nothing]

RULES — these matter:
- Keep it ONE self-contained HTML file. No separate CSS files.
- Do NOT change any of my links or the folder names in them.
- Keep it working on a phone.
- Change nothing else about how it works.

Give me the whole file back in one code block.

Paste it back

  1. Click inside Gemini's code block and copy all of it
  2. Back in your editor, click into index.html
  3. Select everything (⌘A / Ctrl+A) so the new version replaces the old one
  4. Paste
  5. Save — ⌘S / Ctrl+S
Don't skip the select-all. Paste without it and you get the new file jammed on top of the old one — two complete web pages in a single file. It looks like nonsense and it is.
Check you actually saved. In VS Code, an unsaved file shows a ● instead of an ✕ on its tab. Dot means unsaved. Nothing you do next will work if that dot is there. (github.dev saves as you type — nothing to do.)

PART 4Check what changed, then push

Now go and look at what you actually did.

ObjectiveYour changes read and understood, saved with a message, and live on the internet.

Switch to GitHub Desktop. It already knows what you did — it's been watching the folder the whole time.

The Changes tab on the left lists every file you touched. Click index.html.

Click the Source Control icon in the far-left bar — the one shaped like a branching line. It lists every file you changed.

Click the file name to open the comparison view.

What you're looking at is a diff

When a file changes, Git compares the old version to the new one and shows you every line that's different. That's a diff, and it's what fills your screen right now.

<body>
− <h1>Maya</h1>
− <p class="tag">Things I'm building.</p>
+ <h1>maya ✦ makes things</h1>
+ <p class="tag">Games, mostly. Some of them work.</p>

Red with a minus is gone. Green with a plus is new. Grey lines are untouched, shown so you can see where you are.

Nobody writes a diff — it's computed. Git works it out by comparing the two files. Which makes it the only completely honest record of what you did. You can misremember what you changed. This can't.

Read it before you send it

Scroll the whole thing. You're looking for three things:

  • Changes you meant to make. Good — that's your design work.
  • Changes you never asked for. AI rewriting things you didn't mention. Very common. This is your one chance to catch it.
  • Your project link. Find it in the diff. Is it still exactly your-folder-name/?
The link is what breaks. Your project link must stay as your-folder-name/ — folder name, slash, nothing before it. A redesign that turns it into https://… or changes the capitals will break your site, and everything will look perfectly fine until someone clicks it.
The test: if you can't explain a green line, you don't yet know what your own site does. Find out before you commit it.

Now send it

Commit = save this version, with a note about what it is.
Push = send your saved versions up to GitHub.

They're two steps because your repository exists in two places — the copy on your computer and the copy on GitHub. Committing writes to yours. Pushing syncs it to theirs.

  1. Bottom left, type a Summary — what you changed, in a few words
  2. Click Commit to main
  3. The file list empties. That's right — it's saved on your computer now
  4. Top of the window, click Push origin
Committing is not publishing. Stop after committing and your live site is unchanged — you saved to your own computer and told nobody. Push origin is what puts it on the internet, and forgetting it is the single most common mistake with this app.
  1. Click the + next to your changed file (this is "staging" — choosing what goes in)
  2. Type a message in the box — what you changed, in a few words
  3. Click Commit & Push
Why yours is one button and theirs is two. There's no copy of your repository on your iPad — you've been editing GitHub's copy all along. So there's nothing to sync: saving and publishing are the same act. On a laptop they're genuinely two separate events, which is why that app has two buttons.

Good messages: Redesign homepage with green palette · New fonts and spacing
Useless messages: update · changes · asdf

PART 5Test it like a stranger

Your editor showing the right thing is not evidence.

ObjectiveProof your redesign works for someone who isn't you, on a device that isn't yours.

Wait a minute or two, then open your live address in a new tab.

New work breaks old work. You've seen this with levels — you add Level 2 and Level 1 stops working. Redesigning does the same thing to your links. That's why the link check is on this list and not optional.
Still seeing the old version? The site rebuilds on a delay. Wait two minutes, then hard-refresh — Mac: ⌘⇧R  Windows: Ctrl+Shift+R.

PART 6Your workflow from now on

You just did this once with instructions. Now it's a habit.

ObjectiveChange anything on your site, any time, without needing this page open.
1
Pull — in GitHub Desktop, click Fetch origin before you start. Two seconds, and it saves you from the worst problem there is
2
Edit in VS Code — one file at a time, save as you go
3
Read the diff — check it's only what you meant
4
Commit — with a message that says something
5
Push — send it up
6
Test the live site — including every link
Why step 1 matters. You can change your site from your computer or from github.com in a browser. Edit the same file in both without syncing and Git can't tell which version you meant. Pulling first takes two seconds and prevents the whole mess.

FIXESWhen something goes wrong

Find what you're seeing, then read across.

What you're seeingWhat to do
I can't find the folder I cloned GitHub Desktop → Repository menu → Show in Finder / Show in Explorer.
GitHub Desktop shows no changes You didn't save. Look for the ● on the VS Code tab and press ⌘S / Ctrl+S.
My page looks like two pages stacked up You pasted without selecting all first. Select everything, delete, paste the new version cleanly.
I committed but the site didn't change You didn't push. Click Push origin at the top. This is the big one.
Site looks the same after pushing Rebuild delay. Wait two minutes, then hard-refresh.
My project link 404s now The redesign changed it. Open the diff, find the link, set it back to your-folder-name/ — lowercase, trailing slash, nothing before it.
The whole page is blank You pasted only part of the file. Select all of Gemini's code block and paste again.
"This branch is behind" / can't push Something changed on GitHub that you don't have. Click Pull origin first, then push.
The diff is enormous and I didn't do that Gemini reformatted the whole file. Not broken, just noisy — read it before committing, and add "change nothing else" next time.
VS Code says it doesn't trust the folder Click Yes, I trust the authors. It's your own work.
github.dev won't open with . Keyboard layout. Type github.dev in the address bar instead.
