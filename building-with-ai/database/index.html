Your Database

Building with AI — the key, the rules, and who's allowed to do what

Your app has been running on fake rows typed into your own code. Today you build the place that actually remembers — and you decide, in writing, what strangers are allowed to do to it.

PART 1How do these even talk to each other?

Start here. Everything else on this page depends on getting this right.

ObjectiveYou can say which machine talks to which, and what travels between them.

Your code lives on GitHub. Your data is about to live on Supabase. Those are two different companies, two different servers, in two different places.

Discuss

GitHub has your website. Supabase has your data. So how does GitHub send your data to the person visiting your site?

Answer

It doesn't. GitHub and Supabase never speak to each other at all.

Almost everyone gets this wrong the first time, and the wrong version makes everything afterwards confusing. Here's what actually happens.

The browser is in the middle of everything. It is the only thing that talks to both.

So the order is: someone opens your link → GitHub sends them your code → their browser runs that code → the code tells their browser to go ask Supabase for the rows → Supabase sends the rows back → the browser draws them on the screen.

Discuss

Supabase hosts thousands of databases and has never heard of you. When that browser turns up asking for rows, how does Supabase know which database to look in, and whether to answer at all?

Answer

Two pieces of information, and they have to be written inside your code, because your code is the only thing the browser has.

The project URL — which database. The publishable key — who's asking. That's Part 2.

PART 2The two things your code carries

An address and a name tag. Neither is a secret.

ObjectiveYou can explain what the publishable key does, and why it being public isn't a mistake.

Supabase gives every project these two values. You'll paste both into your code.

Project URL — which database
https://abcdefghijklm.supabase.co

Every Supabase project gets its own web address, built from a random ID. This is how the browser knows which of Supabase's thousands of databases to knock on. It's just an address, the same way your GitHub Pages URL is just an address.

Publishable key — who's asking
sb_publishable_xxxxxxxxxxxxxxxxxxxx

A long string that says one thing: "I'm a member of the public." Not who you are. Not that you're allowed anything. Just that you're an ordinary visitor rather than the owner.

Discuss

That key is going to sit in your JavaScript, which sits in your public GitHub repo, which anyone on earth can read. Is that a mistake?

Answer

No. It's exactly what that key is for.

Think about where your code actually runs. Not on your laptop — on the phone of whoever opened your link. GitHub hands them a complete copy of your HTML, your CSS and your JavaScript. It's on their device now. Right-click, View Source, and every character of it is there.

You cannot hide anything in a website's front end. Not a key, not a password, not a comment about your teacher. So the publishable key was never a secret that leaked — it's an address label, and labels are meant to be read.

The sentence worth remembering: your app doesn't run on your computer. It runs on theirs. Anything your app needs in order to work, they have.
Discuss

If every single visitor gets that key handed to them, what stops one of them deleting everything in your table?

Answer

Right now? Nothing. That's Part 4, and it's the actual problem this lesson exists to solve.

The answer isn't hiding the key better. It's that the key only gets you to the door. Something else decides what you're allowed to do once you're through it.

PART 3Make your project and your table

Roughly fifteen minutes, and the project takes a couple of those on its own.

ObjectiveA live Supabase project with your table in it, holding your rows.
Save the database password somewhere. You won't need it this year, but "I'll remember it" is how people lose a project. Put it wherever you keep passwords.

Now make your table — with SQL

SQL is how you write instructions to a database instead of clicking. You'll use about five sentences of it today. Gemini writes the two long ones; you write the short ones, because those are where the understanding is.

Ask it three questions yourself

Your plan file says your app does three things with the saved rows — filter, sort, count, whatever you chose. Do all three by hand, right now. When your app connects next week, it'll be doing exactly this.

select * from your_table_name;

select * from your_table_name where kind = 'quiet';

select * from your_table_name order by rating desc;

select count(*) from your_table_name;

PART 4The problem

Supabase is about to tell you off. It's right to.

ObjectiveYou can state, in one sentence, what is currently wrong with your table.

Your table is sitting there with a red ERROR on it:

Table publicly accessible
Anyone with your project URL can read, edit, and delete all data in this table because Row-Level Security is not enabled.
Discuss

You just made this table thirty seconds ago and you've told nobody about it. Why does that warning matter?

Answer

Because of what happens next week. The moment you paste your project URL and publishable key into config.js and push it, both of those values are public — and the warning says anyone with your project URL.

Right now it's a locked room nobody knows about. Next week you print the address on the front of your website.

PART 5Row Level Security

Three states. Yours is currently the first one.

ObjectiveYou can explain why turning security on breaks everything, and why that's correct.

State 1 — the door is open

A table made with SQL has no security on it at all. Anyone holding your key can read every row, add rows, change rows, and delete the lot. This is where your table is right now.

State 2 — the door is locked

You switch Row Level Security on. Now nobody can do anything — not strangers, not your app, not you. A locked table with no rules answers every request with nothing at all.

This surprises everyone, and it's the correct behaviour. The database refuses by default.

State 3 — you cut exactly the keys you want

You write rules, called policies. Each one names one action and who may do it. This unit you write exactly two: anyone may read, anyone may add.

You never write "anyone may delete." So nobody can — including you, from your own app.

Discuss

Why would a database be built to refuse everything by default? Wouldn't it be friendlier to allow everything and let you switch off the bits you don't want?

Answer

Because of what each mistake costs you.

If the default is "refuse" and you forget a rule, your app doesn't work — annoying, obvious, fixed in a minute. If the default is "allow" and you forget a rule, your data is public — and nothing looks wrong at all. You find out when someone tells you.

One mistake announces itself. The other hides. Sensible systems are built so the loud mistake is the one you make.

Put this one in your notes: you don't get what you forgot to forbid. You get what you explicitly allowed.

PART 6Lock it, then open two doors

Three statements. Read each one before you run it.

ObjectiveRLS on, two policies written, and the red error gone.

Swap your_table_name for your actual table name in all three.

alter table public.your_table_name enable row level security;
create policy "Anyone can read"
on your_table_name for select
to anon
using ( true );
create policy "Anyone can add"
on your_table_name for insert
to anon
with check ( true );

Reading those out loud

  • for select / for insert — which action this rule is about. One rule, one action.
  • to anon — who it applies to. anon means anonymous: anyone who hasn't signed in, which this unit is everybody. Next unit you'll meet authenticated.
  • using ( true ) — which rows they may see. true means all of them.
  • with check ( true ) — which rows they're allowed to add. true means anything.

Reading rules use using. Adding rules use with check. Swap them and you get an error — it's the most common typo on this page.

The dashboard is signed in as you, the owner. It can see your rows whatever your policies say, so it can't honestly tell you whether a policy works. To test as an ordinary visitor, say so explicitly: 
set role anon;
select * from your_table_name;
reset role;

That runs the query as a stranger would. This is your test bench for everything in Part 7 — and don't forget reset role; at the end, or the rest of your queries keep pretending to be a visitor.

PART 7The policy playground

Break it on purpose. It's your database and there's nothing in it but rows you invented.

ObjectiveYou've seen a rule change what's possible, without touching a single line of your app.

Predict before you run. Say out loud what you think will happen, then run it and see whether you were right. Being wrong is the part that teaches you something.

Test each one with the set role anon; block from Part 6.

A

Take away the reading rule

drop policy "Anyone can read" on your_table_name;

Predict: what does a visitor see now — an error, or something else?

What it proves: no policy means no access, and it fails silently — you get zero rows, not an error message. An app with no reading rule looks empty, not broken. Put it back before moving on.
B

Only let people see some of the rows

Change kind = 'quiet' to a column and value that exist in your own table.

drop policy "Anyone can read" on your_table_name;

create policy "Anyone can read"
on your_table_name for select
to anon
using ( kind = 'quiet' );

Predict: your app's code still says "get everything." So what comes back?

What it proves: the filtering happens at the database, before anything is sent. Your app asked for all the rows and was handed some of them, and it has no way of knowing the others exist. This is how Unit 3 works — swap that rule for "only rows belonging to whoever is signed in" and you've built private data.
C

Let anyone delete anything

create policy "Anyone can delete"
on your_table_name for delete
to anon
using ( true );

Predict: you haven't changed your app at all. Can a stranger now empty your board?

What it proves: the rule is the permission — not whether your page has a delete button. Anyone can send a delete request by hand; your buttons are a suggestion, not a lock. Drop this policy before you leave. You do not want it on a public board.
drop policy "Anyone can delete" on your_table_name;
D

Refuse anything too long

Use one of your own text columns instead of comment.

drop policy "Anyone can add" on your_table_name;

create policy "Anyone can add"
on your_table_name for insert
to anon
with check ( char_length(comment) < 100 );

Predict: your app has no length limit anywhere in it. Try inserting a 300-character row as anon.

What it proves: the database enforces this, and a visitor cannot get round it — not by editing your page, not by turning off your JavaScript, not by sending the request themselves. This is the first rule you've written that can't be bypassed, and it's only because it lives somewhere the visitor can't reach.
E

Make it read-only

drop policy "Anyone can add" on your_table_name;

Predict: can people still read the board? Can they still post to it?

What it proves: reading and adding are separate permissions and don't imply each other. An archive that anyone can read and nobody can add to is one dropped policy away.
F

Put it back the way it should be

End the period here. Your table should have RLS on and exactly two policies: read, and add.

select policyname, cmd
from pg_policies
where tablename = 'your_table_name';
