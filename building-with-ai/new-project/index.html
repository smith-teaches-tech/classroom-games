Adding a New Project

Building with AI — making folders and files on your own computer

Until now you've only edited files that were already there. Today you make your own — a new folder, new files, from nothing — and push them up. This is the workflow you'll use for every project for the rest of the year.

Read this first

By the end of the period your app has its own web address and a card on your homepage.

  1. Make a folder and files on your own computer — not on github.com. Every project you've touched so far already existed. Starting one from nothing is the step you've never done, and it's the one that unlocks working on your own.
  2. Build Build 1 inside that folder from the start. This isn't somewhere you copy your app when it's finished. It's where you write it. Set the folder up first, then do all your building in it — every save lands in the right place and there's nothing to move later.
  3. Understand that saving and pushing are two different things. Saving puts a file on your computer. Pushing puts it on the internet. You'll save thirty times and push three times today, and knowing which one you just did is how you'll fix things when they break.
  4. See your app before you push it. Waiting for GitHub to rebuild after every tiny change will eat your whole period. You'll set up a two-window loop instead — edit, save, refresh — and only push when something actually works.
  5. Link the new project from your homepage. A folder nobody can find isn't finished. One more folder, one more address, one more card — the same move you'll repeat for every build this year.
  6. Keep project.md current before you close anything. Your next chat with Gemini knows nothing about your project except what's in that file. Whatever you don't write down, you'll have to explain again from scratch.

Same three apps as last time, one new job. The only genuinely new thing today is the second box: making a folder and files that didn't exist before.

Set the folder up first. Then build in it.

Parts 1–3 take about ten minutes, and you do them before you have any code at all. After that, your Build 1 app gets written inside that folder — not on your Desktop, not in Downloads, not somewhere you'll move later.

Why it matters: everything you save is already in the right place, so pushing is one click instead of a hunt. And you can push half-finished work at any point — which you should, because a push is also a backup.

Already started building somewhere else? Fine. Do Parts 1–3 now, paste what you've got into the new files, and carry on from there.

PART 1Open your repo

Get your whole site open in VS Code before you touch anything.

ObjectiveYour repository is up to date and open in VS Code, with the file list showing in the sidebar.

Open GitHub Desktop. Check the repository name at the top left — it should say yourusername.github.io. If it doesn't, click it and pick the right one.

If that opens the wrong app, your default editor isn't set. Go to GitHub Desktop → Settings (Windows: File → Options) → Integrations → set External editor to Visual Studio Code. Then try again.

You should now see your whole site in VS Code's left sidebar — index.html, your game folder, README.md. That's your website, sitting on your computer.

No GitHub Desktop and no VS Code on iPad, so you work in github.dev — which is the same editor, running in your browser.

You don't need to fetch — you're editing the real repository directly, so it's always current. Everything else on this page works the same, except the preview in Part 5. Read the iPad tab there.

PART 2Make the folder

This is the step you've never done before.

ObjectiveA new, correctly named folder sitting inside your repository.

The naming rules are not suggestions

This folder name becomes part of a web address, so it has to survive on the internet:

  • all lowercase
  • dashes, never spaces
  • letters, numbers and dashes only
  • short, because people have to type it
Yes

shoutout-board
study-spots
song-picks

No

Shoutout Board
Study_Spots
songPicks

This is still the number one bug in this room. Your laptop thinks Study-Spots and study-spots are the same folder. The web does not. Your link will work perfectly on your machine and 404 for everyone else.

Remember what a folder actually gets you:

study-spots/ → yourname.github.io/study-spots/

PART 3Make the files

Empty files first — you don't need any code yet.

ObjectiveEvery file your app needs, created and correctly named, inside your new folder.
Your looking view has to be called index.html. Not home.html, not Index.html. It's the front door — the file a server shows when someone types your address with nothing after it. Same magic name as your game folder.

A typical project folder:

study-spots/ index.html your looking view — where visitors land add.html your adding view — name it whatever fits style.css how it looks, if you have one app.js what it does, if you have one project.md your plan. Yes, it lives here too
You don't have to make all of them now. Start with index.html and project.md. Add the rest when you actually need them — new file, same two clicks.

Which view should be index.html?

Think about the Tuesday test from your plan. The person who opens your app with nothing to add is the one who lands on the front door.

For almost every project that means the looking view is index.html, with a link across to the adding view. If you're doing it the other way round, you should be able to say why.

PART 4Build inside it

This is the rest of your period. The folder is ready — now fill it.

ObjectiveYour app is being written inside your repo, and saved as you go.

Open a chat with Gemini, paste in your project.md, and build your app one piece at a time. Everything it hands back gets pasted into the files you just made.

Copy the whole thing. Click inside the code block, then ⌘A / Ctrl+A, then copy. Half a file pasted gives you a blank page, and that is still the most common bug in this room.
Look at the file's tab. A white dot instead of an × means unsaved. GitHub Desktop cannot see unsaved changes. If you push and nothing happens, this is why, nine times out of ten.

PART 5Look at it before you push

Stop waiting for GitHub. You don't have to.

ObjectiveA browser tab showing your app from your own computer, that you refresh instead of pushing.

Pushing and waiting for the site to rebuild takes a couple of minutes. If you do that after every change you will get through about six changes today. Here's the alternative.

Your loop from here on:

VS Codeedit ▸ ⌘S / Ctrl+Ssave ▸ Browserrefresh
Push only when something actually works. Not after every change. This loop takes about two seconds; pushing takes about two minutes.

An iPad can't open a local file and run it — you already know this from the escape rooms. There's no local preview in github.dev either.

So your options are the same two as always:

  • Cloudflare Drop for a quick check — upload, open the link, test it.
  • Push and wait — which is fine, as long as you do it in bigger chunks than everyone else.

Get several things done, then check. You'll make fewer round trips than the people refreshing every ten seconds.

PART 6Push it

Not once at the end — every time something works.

ObjectiveYour project is live at its own web address, and stays current as you build.
Push early and push often. Your first push can happen when the folder holds nothing but an empty index.html. A push is also a backup — if your laptop dies tonight, everything you pushed is safe and everything you didn't is gone.

Back to GitHub Desktop. Your new files are all listed on the left — every one of them, because every one of them is new.

Wait 1–3 minutes, then open your new address:

https://yourusername.github.io/your-folder-name/

Saving and pushing are two different things

Saving writes the file to your computer. Pushing copies it to GitHub, which then puts it on the web.

You'll save thirty times and push three times today. When something isn't showing up, the first question is always: did I save it, or did I push it?

PART 7Link it from your homepage

A folder nobody can find isn't finished.

ObjectiveA second card on your homepage that opens your new app.

The link is just your folder name and a slash:

href="your-folder-name/"
Not a full https:// address. That's a relative link — it means "the folder sitting next to this file" — and it keeps working no matter what your site's address is.

PART 8Test it properly

Five checks. Do them now, not next week.

ObjectiveEvidence it works for someone who isn't you, on a device that isn't yours.

PART 9Update project.md

Before you close a single tab.

ObjectiveYour plan file describes the app as it is right now, and it's pushed.
Your next chat with Gemini knows nothing. Not what your app is, not what you built today, not what's broken. Whatever isn't in project.md is gone, and you'll spend the first twenty minutes of next class explaining your own project back to a machine.

Ask the chat that just did the work, while it still remembers everything:

Update my project file. Fill in "Where we are right now", add a line to
the change log, and give me the whole file back in one code block.
Your plan now lives in the same folder as the app it describes, and every version of it is kept. This is the Close-Out you've been doing since Class 4 — it just runs through GitHub now.

Before you ask for help

Say what you expected and what actually happened. "It doesn't work" isn't something anyone can act on. "I pushed, waited three minutes, and the address still 404s" is.
