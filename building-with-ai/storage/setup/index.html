Set Up Files and Usernames

The step-by-step. If you haven't read Saving Files yet, start there. You need its four decisions before step 1.

Your four decisions (from the lesson, written in your project file): which file types · who can see the files · your size limit · your bucket's name.
The list

What you need to do, in order

Users first, then the place files go, then the rules, then the code. Each step needs the one before it.

The screens below are mock-ups. Your screen may look a little different, but the setting names will be close. Our examples use a table called profiles and a bucket called user-files. Use your own names, and spell them exactly the same everywhere.

1

Make your users table: ask Gemini

Gemini

Supabase already keeps everyone's account (email and scrambled password) in its own table, auth.users. You don't touch that one. But your app needs to know things Supabase doesn't: a username, maybe a bio or a display name. Those go in your own table, usually called profiles, with one row per user.

Supabase's tableauth.users

Email, scrambled password, sign-in details. Made for you. Hands off.

Your tableprofiles

Username and anything else your app shows. Linked to the account by the same ID.

Paste this prompt into Gemini. Fill in the [brackets] with what your app needs. Pick the view rule that matches your sharing decision.

Why "no trigger"? Many examples online use a trigger that makes the profile row automatically at sign-up. If that trigger has one mistake in it, nobody can sign up at all. It's safer for your app to make the row the first time someone signs in.
Prompt · fill in the [brackets]
Write Supabase SQL to create a table called profiles, with one row for each user of my app. Columns: - id: the user's ID from auth.users. This is the primary key. If the account is deleted, delete the row too. - username: text, unique, 3 to 20 characters. - created_at: when the row was made. - [any other columns my app needs, for example display_name or bio] Turn on row level security, then add these policies: 1. Create: a signed-in user can create only their own row (id must equal auth.uid()). 2. Update: a signed-in user can update only their own row. 3. View: [pick one: only the owner can see their row / any signed-in user can see usernames]. 4. Nobody can delete rows from the app. Do not use a trigger. My app will create the row after someone signs in. Do not change auth.users or any other table. Only create this table and its policies. After the SQL, explain each part in one plain sentence.
1b

Check it, then run it

Supabase

Your project → SQL Editor (left menu) → New query → paste → Run

Before you click Run, check what Gemini wrote:

  • It says create table … profiles, and id references auth.users.
  • It has enable row level security.
  • Create and update policies check auth.uid() = id.
  • No create trigger, and nothing that changes auth.users.

You should see Success. No rows returned. That's good news for this kind of SQL. Open the Table Editor: your profiles table is there, empty until someone signs in. If something looks wrong, paste it back into Gemini and ask what it does before running it.

Make your bucket

Supabase

Your project → Storage (left menu) → New bucket

  1. Name: short, lowercase, dashes. For example user-files. Write it down exactly.
  2. Public bucket: leave it off, unless your level is "Anyone on the internet".
  3. Restrict file size: turn it on, type 10 MB.
  4. Allowed MIME types: turn it on and paste the list below. (A MIME type is a file's label, like image/png.) Delete any type your app doesn't need.
  5. Click Save or Create.
Allowed MIME types
image/jpeg, image/png, image/webp, image/gif, video/*, audio/*, application/pdf, application/vnd.openxmlformats-officedocument.wordprocessingml.document

Missed a setting? Click the bucket's three-dot menu → Edit bucket.

3

Add the file rules: ask Gemini

Gemini

The policies are a few lines of SQL. Your AI writes them, but you give it the rules. Fill in the blanks in this prompt: your bucket name and your sharing decision.

Good prompts for SQL name four things:

  1. The table: storage.objects. That's where Supabase keeps a row for every file.
  2. The bucket name, spelled exactly.
  3. The folder rule: every file is saved inside a folder named after the user's ID.
  4. Each action separately: upload, view, delete. Say who can do each one.
Ask it to explain. The last line of the prompt asks for one plain sentence per policy. If you can't explain a policy, you can't draw it in your diagram, and you shouldn't run it.
Prompt · fill in the [brackets]
Write Supabase SQL policies for the storage.objects table, for my storage bucket named [user-files]. Every file is saved inside a folder named after the user's ID, like this: [user id]/[file name]. Rules: 1. Upload: signed-in users can upload only into their own folder. 2. View: [pick one: only the owner can view their own files / any signed-in user can view files in this bucket]. 3. Delete: signed-in users can delete only files in their own folder. 4. Nobody can update or overwrite files. Use storage.foldername(name) and auth.uid() to check the folder. Use "to authenticated". Only create policies. Do not drop, delete or disable anything. After the SQL, explain each policy in one plain sentence.
3b

Check it, then run it

Supabase

SQL Editor → New query (a fresh one) → paste → Run

Before you click Run, check what Gemini wrote:

  • Every policy says on storage.objects.
  • Every policy has bucket_id = 'user-files' with your bucket name, spelled exactly.
  • Upload and delete say to authenticated.
  • Upload and delete compare (storage.foldername(name))[1] with auth.uid().
  • There's a view (select) policy. Without one, uploads fail too. Supabase needs to read the file's details back after saving it.
  • No with check (true) or using (true) on upload or delete. That means "anyone, anywhere".
  • No drop, truncate, delete from or disable row level security. If you see one, don't run it. Ask your AI why it's there.

You should see Success. No rows returned. Your rules now show under Storage → Policies.

New query

create policy "Upload to own folder" on storage.objects for insert to authenticated with check ( bucket_id = 'user-files' and (storage.foldername(name))[1] = (select auth.uid()::text) ); -- …view and delete policies…
Success. No rows returned
Stuck? See what good SQL looks like (Only me level)

Compare this with what your AI wrote. For "People signed in to my app", the view policy only checks the bucket: using (bucket_id = 'user-files').

create policy "Upload to own folder" on storage.objects for insert to authenticated with check ( bucket_id = 'user-files' and (storage.foldername(name))[1] = (select auth.uid()::text) ); create policy "View own files" on storage.objects for select to authenticated using ( bucket_id = 'user-files' and (storage.foldername(name))[1] = (select auth.uid()::text) ); create policy "Delete own files" on storage.objects for delete to authenticated using ( bucket_id = 'user-files' and (storage.foldername(name))[1] = (select auth.uid()::text) );
4

Add the code: ask Gemini

Gemini

Upload index.html, app.js and config.js, then paste this. Fill in the [brackets] to match your table and bucket.

Why the prompt is so detailed: AI often makes a "progress bar" that's just an animation, not connected to the real upload. Item 5 asks for the real thing. You'll test it in step 5.
Why the app checks too: the bucket already blocks big or wrong files. The app's check is the sign on the door: it gives a friendly message straight away, instead of a confusing error after waiting.
Prompt
I'm adding usernames and file uploads to my app. My files are index.html, app.js and config.js (attached). Sign-in already works with Supabase. I made a profiles table (id, username[, other columns]) with row level security. My Supabase storage bucket is named [user-files]. It is [private / public]. Files can be up to 10 MB. Allowed types: JPG, PNG, WEBP, GIF, video, audio, PDF and Word (.docx). Please add: 1. The first time someone signs in and has no row in profiles, ask them to pick a username and save their row. If the username is taken, say so and let them try another. Show their username at the top of the page. 2. An "Add file" button. Use a file input with an accept attribute that only lists my allowed types. 3. Before uploading, check the file's size and type in the browser. If it's too big or the wrong type, show a clear message and don't upload. 4. Save each file at [user id]/[timestamp]-[file name], so two files never have the same name. 5. A progress bar that shows the REAL upload progress as a percentage, using an upload method that reports progress. Not a fake animation. Disable the Add file button while a file is uploading. 6. A list of my files with name, size and a Delete button. 7. Show files on the page: photos with an img tag, videos with a video tag, audio with an audio tag, PDF and Word files as a link that opens in a new tab. If my bucket is private, use signed URLs. 8. Show any error from Supabase on the page in plain words. Do not put any secret keys in my code. Change nothing else. Tell me exactly which file each change goes in.
Step 5

Test it, then try to break it

Tick each one off on your live GitHub Pages site.

Error decoder

These are almost always a setting or a policy, not your app's code.

You seeWhat's wrongFix
new row violates row-level security policyA policy is missing, or the file isn't going into a folder named after the user's ID. A missing view policy causes this too.Step 3b checklist. Check the file path starts with the user's ID.
duplicate key value violates unique constraintSomeone already has that username. Working as planned.Make sure your app turns this into "That username is taken."
new row violates row-level security policy for table "profiles"The app is saving a profile row whose id isn't the signed-in user's ID, or the create policy is missing.Step 1b checklist. The row's id must be the user's ID.
Bucket not foundThe bucket name in your code doesn't match the name in Supabase.Compare them letter by letter. Capitals and dashes count.
The object exceeded the maximum allowed sizeThe file is bigger than your bucket's limit. Working as planned.Make sure your app catches this first, with a friendly message.
mime type … is not supportedThe file's type isn't on your bucket's allowed list. Working as planned, unless it's a type you meant to allow.Step 2: Edit bucket. Check the allowed list.
The resource already existsA file with that exact name is already in the folder.Step 4, item 4: add a timestamp to every file name.
Photos upload but show as broken imagesThe bucket is private, so plain links don't work.Ask your AI to use signed URLs to show files.
What about phones? Your Add file button already works on phones. It opens the camera and photo library for free. Turning your app into a real phone app (installed on the home screen, built for small screens first) comes in a later unit. For now, just make sure uploading from a phone works.
