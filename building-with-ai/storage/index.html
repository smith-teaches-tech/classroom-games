Part 1

Where files live

Your database tables hold words and numbers. Files are too big for that, so Supabase keeps them in Storage, inside a bucket. A bucket is like a shared drive for your app.

Inside the bucket, every person gets their own folder, named after their account ID. Then you write policies (rules, in SQL) that check the folder name. It's the same RLS idea as your tables: "you can only touch your own stuff."

SQL, written with your AIThe policies

Who can upload, view and delete. Until you add policies, nobody can upload anything. Supabase locks new buckets by default.

Your app's checks are a sign on the door: they help honest people. The bucket settings and policies are the lock: they stop everyone, because they run on Supabase, not in the browser.

Part 2

What to let in

Supabase does not scan files for viruses. So you decide what kinds of files your bucket accepts. Your apps share photos, videos, audio and documents, so those are in. Some file types should never be allowed, because they can carry code that runs.

Allow

  • Photos · JPG, PNG, WEBP, GIF
  • Video · MP4, MOV (iPhone), WEBM
  • Audio · MP3, M4A (voice memos), WAV
  • Documents · PDF, Word (.docx)

These hold pictures, sound or text. On their own, they don't run code.

Never allow

  • .html .htm · a web page. Opened from your storage link, it runs its own code. It could pretend to be your sign-in page.
  • .svg · looks like a picture, but it's written as code and can hide a script.
  • .exe .msi .apk .dmg · programs. Run one and it can do anything on that computer.
  • .zip .rar .7z · sealed boxes. Nobody can see what's inside until it's opened.
  • .docm .xlsm .pptm · Office files with macros, little programs that run when the file opens. (.docx can't have macros. .docm can.)
  • .js .bat .sh · code files.
The trap with "all images": Supabase lets you allow image/*, meaning every image type. But SVG counts as an image type. So list your photo types one by one instead. Video and audio are fine to allow as a group (video/*, audio/*).

Part 4

How big

Your Supabase account is free, and free has limits. One person uploading a few long videos could fill your whole account. So your bucket gets a size limit.

50 MBBiggest single file a free account allows
1 GBAll files, all buckets, for your whole Supabase account (both projects)
10 MBOur class limit per file. About 100 files fill 1 GB.
~1 MBper second of normal phone video. 10 MB is about 10 seconds.
Video is the problem child. A phone photo is usually 2 to 5 MB and fits easily. A one-minute phone video is around 60 MB and won't fit. If your app shares video, keep clips short, record at a lower quality, or raise the limit (up to 50 MB) and accept that your 1 GB fills up faster. Write your choice in your project file.

2

Ask your AI to write the policies

Your AI

The policies are a few lines of SQL. Your AI writes them, but you give it the rules. Fill in the blanks in this prompt: your bucket name and your sharing level from Part 3.

Good prompts for SQL name four things:

  1. The table: storage.objects. That's where Supabase keeps a row for every file.
  2. The bucket name, spelled exactly.
  3. The folder rule: every file is saved inside a folder named after the user's ID.
  4. Each action separately: upload, view, delete. Say who can do each one.
Ask it to explain. The last line of the prompt asks for one plain sentence per policy. If you can't explain a policy, you can't draw it in your diagram, and you shouldn't run it.
Prompt · fill in the [brackets]
Write Supabase SQL policies for the storage.objects table, for my storage bucket named [user-files]. Every file is saved inside a folder named after the user's ID, like this: [user id]/[file name]. Rules: 1. Upload: signed-in users can upload only into their own folder. 2. View: [pick one: only the owner can view their own files / any signed-in user can view files in this bucket]. 3. Delete: signed-in users can delete only files in their own folder. 4. Nobody can update or overwrite files. Use storage.foldername(name) and auth.uid() to check the folder. Use "to authenticated". Only create policies. Do not drop, delete or disable anything. After the SQL, explain each policy in one plain sentence.
3

Check the SQL, then run it

Supabase

Your project → SQL Editor (left menu) → New query → paste → Run

Before you click Run, check the SQL your AI gave you:

  • Every policy says on storage.objects.
  • Every policy has bucket_id = 'user-files' with your bucket name, spelled exactly.
  • Upload and delete say to authenticated.
  • Upload and delete compare (storage.foldername(name))[1] with auth.uid().
  • There's a view (select) policy. Without one, uploads fail too. Supabase needs to read the file's details back after saving it.
  • No with check (true) or using (true) on upload or delete. That means "anyone, anywhere".
  • No drop, truncate, delete from or disable row level security. If you see one, don't run it. Ask your AI why it's there.

After you run it, you should see Success. No rows returned. That's good news for this kind of SQL.

New query

create policy "Upload to own folder" on storage.objects for insert to authenticated with check ( bucket_id = 'user-files' and (storage.foldername(name))[1] = (select auth.uid()::text) ); -- …view and delete policies…
Success. No rows returned

create policy "Upload to own folder" on storage.objects for insert to authenticated with check ( bucket_id = 'user-files' and (storage.foldername(name))[1] = (select auth.uid()::text) ); create policy "View own files" on storage.objects for select to authenticated using ( bucket_id = 'user-files' and (storage.foldername(name))[1] = (select auth.uid()::text) ); create policy "Delete own files" on storage.objects for delete to authenticated using ( bucket_id = 'user-files' and (storage.foldername(name))[1] = (select auth.uid()::text) );
4

Ask your AI for the Add file button

Your AI

Upload index.html, app.js and config.js, then paste this. Fill in the [brackets] to match your bucket.

Why the prompt is so detailed: AI often makes a "progress bar" that's just an animation, not connected to the real upload. Item 4 asks for the real thing. You'll test it in Part 6.
Why the app checks too: the bucket already blocks big or wrong files. The app's check is the sign on the door: it gives a friendly message straight away, instead of a confusing error after waiting.
Prompt
I'm adding file uploads to my app. My files are index.html, app.js and config.js (attached). Sign-in already works with Supabase. My Supabase storage bucket is named [user-files]. It is [private / public]. Files can be up to 10 MB. Allowed types: JPG, PNG, WEBP, GIF, video, audio, PDF and Word (.docx). Please add: 1. An "Add file" button. Use a file input with an accept attribute that only lists my allowed types. 2. Before uploading, check the file's size and type in the browser. If it's too big or the wrong type, show a clear message and don't upload. 3. Save each file at [user id]/[timestamp]-[file name], so two files never have the same name. 4. A progress bar that shows the REAL upload progress as a percentage, using an upload method that reports progress. Not a fake animation. Disable the Add file button while a file is uploading. 5. A list of my files with name, size and a Delete button. 6. Show files on the page: photos with an img tag, videos with a video tag, audio with an audio tag, PDF and Word files as a link that opens in a new tab. If my bucket is private, use signed URLs. 7. Show any error from Supabase on the page in plain words. Do not put any secret keys in my code. Change nothing else. Tell me exactly which file each change goes in.

Error decoder

These are almost always a setting or a policy, not your app's code.

You seeWhat's wrongFix
new row violates row-level security policyA policy is missing, or the file isn't going into a folder named after the user's ID. A missing view policy causes this too.Step 3 checklist. Check the file path starts with the user's ID.
Bucket not foundThe bucket name in your code doesn't match the name in Supabase.Compare them letter by letter. Capitals and dashes count.
The object exceeded the maximum allowed sizeThe file is bigger than your bucket's limit. Working as planned.Make sure your app catches this first, with a friendly message.
mime type … is not supportedThe file's type isn't on your bucket's allowed list. Working as planned, unless it's a type you meant to allow.Step 1: Edit bucket. Check the allowed list.
The resource already existsA file with that exact name is already in the folder.Step 4, item 3: add a timestamp to every file name.
Photos upload but show as broken imagesThe bucket is private, so plain links don't work.Ask your AI to use signed URLs to show files.
What about phones? Your Add file button already works on phones. It opens the camera and photo library for free. Turning your app into a real phone app (installed on the home screen, built for small screens first) comes in a later unit. For now, just make sure uploading from a phone works.
